用 AI + REA 逆向极米投影仪的局域网遥控协议：过程、踩坑与工具的局限

发表于2026-10-18|更新于2026-10-18|技术笔记
|浏览量:

家里的极米投影仪，手机遥控要用「极米助手」——一个 208MB、带商城、社区、IM 的超级 App，还时不时让你登录。我想要的只是一个干净的局域网遥控器。

这次我想顺便试试 REA（Reverse Engineer Anything）这个面向 AI agent 的逆向工具，让 Claude Code 用它来分析 APK。最后遥控器做出来了，基本可用；但说实话，REA 在这个项目里几乎没派上用场。本文按时间线记录整个过程、每个坑是怎么解决的，以及我对 REA 和”AI 做逆向”这件事的局限性的看法。

一、起因和目标

投影仪和手机在同一个局域网里，遥控理论上只需要局域网通信，没理由非要登录账号。最初的需求很朴素：

  1. 搞清楚极米助手的遥控到底依不依赖账号；
  2. 如果不依赖，做一个免登录、只有遥控功能的东西。

最终交付的是一个 Flutter 写的手机遥控 App（release 包 7MB），外加一个 Python/Tkinter 写的 PC 版遥控工具。手机版的界面尽量照着原版遥控页布局，降低使用成本：

功能 状态
方向键 / OK / 返回 / 主页 / 菜单 / 音量± ✅
电源菜单：立即关机、系统关机菜单、定时关机（15/30/60/120 分钟）、取消定时 ✅
全部设置（投影仪快捷菜单） ✅
画面校正（自动梯形校正） ✅
对焦 + / 对焦 − ✅
局域网自动发现、切回前台自动重连 ✅
自动对焦 ❌ 未解决（见后文）
语音、截图、应用列表 ⏸ 暂未实现

二、REA 是什么

REA 是一个 MCP server，把一堆逆向工具（Ghidra、Hopper、IDA、JADX、Frida、GDB、Rizin、adb、浏览器 CDP……）包装成统一接口给 AI agent 调用。它的几个设计理念我挺认同：

  • 证据优先：每个结果都带 Evidence 记录（目标文件的 SHA-256、使用的分析引擎、覆盖范围和局限），区分”观察到的”、”推断的”和”未知的”；
  • 目标内容不可信：从二进制里读出的字符串、反编译代码一律标记为不可信数据，防止被逆向目标里的文本做提示词注入；
  • 先摘要再深入：大结果先返回摘要，再按需翻页，避免一次把上下文塞爆。

安装很简单：npx rea-agents setup，它会把 MCP server 注册到 Claude Code，并附带一份 skill（使用说明）。

四、REA 实际用上了多少

先说结论：REA 暴露了 207 个工具，整个项目里实际只调用了 1 次，而且失败了。

4.1 第一个坑：装完了，但当前会话里没有

npx rea-agents setup 之后，在同一个 Claude Code 会话里直接开始分析。rea-agents doctor 报告注册状态健康，但当前会话里并没有 REA 的工具——MCP server 是在会话启动时加载的，装完需要重启 agent 才会出现。这一点 REA 的文档里写了，doctor 也明确提示”注册正常不代表当前会话已连接”，但第一次用很容易忽略。

4.2 第二个坑：Android 分析要自备 JADX

后来工具加载进来了，我调用了 inspect_android_package 分析 APK，返回：

REA 的 Android 能力依赖一个需要用户自己准备的 jadx-headless-mcp JAR，REA 明确不负责下载和安装任何分析引擎（Ghidra、IDA、JADX、Binwalk 都是如此）。这是有意的设计——不替用户往机器上装东西、版本由用户掌控——但对”想快速试一下”的人来说，门槛就在这里。

4.3 第三个坑：公司网络

想顺手装个 JADX，结果 GitHub API 返回空响应（公司网络拦了 api.github.com，下载域名倒是通的）；后面构建 Flutter 时，Google Maven 也被拦了。在受限网络下，”自备引擎”这件事的成本会被放大。

4.4 退回经典工具链

机器上正好有一个现成的 apktool.jar，于是整个静态分析就变成了最朴素的组合：

Windows 的 Git Bash 里连 strings 都没有，看二进制 Manifest 的字符串池就用 tr -d '\000' | grep -aoE ... 凑合。

说实话，对这个 APK 来说，apktool + grep 已经够用了：它没有加固、没有原生壳、没有插件化，6 个 dex 反编译出来就是可读的 smali，类名方法名都没混淆。真正的难点不在”读代码”，而在”读对代码”——下一节的坑几乎都是这一类。

五、静态分析的坑，以及怎么解决的

5.1 鉴权架构：结论是对的

先说一个做对了的判断。通过读 ConnectParameter、AuthCode、VcontrolCmd 这几个类：

  • 连接参数是 ip + port + phoneName + phoneUid + authCode + timeout，没有账号 token；
  • AuthCode 是投影仪本地配对的模型：无需授权 / 弹窗确认 / 输入投影仪上显示的验证码 / 永久信任；
  • 没有全局登录拦截器，登录只是个别功能入口里的软判断。

所以”遥控不需要登录”这个直觉是对的。后来真机验证：连上 TCP 发一个连接命令，投影仪直接回设备信息，连验证码都没要。

5.2 改包免登录：卡在云端绑定

既然遥控不依赖登录，最初尝试的是改极米助手本身：跳过登录、直达遥控页，改包名以便和原版共存。改包本身没问题（无加固、可重签），但在”添加设备”这一步卡住了——设备列表来自账号下的云端绑定，不登录就拿不到设备，局域网直连的入口又藏在这个流程后面。继续改下去等于要重写它的设备管理，于是放弃，转向自己写独立遥控器。

5.3 端口 57418：把魔数当成了端口

第一版遥控器连接投影仪，直接 errno 111 ECONNREFUSED。

回头查，当初在 ProtocolHeader 里看到 magicNumber = 0xe04a，换算成十进制 57418，就当成了端口——它其实是帧头的魔数。真正的端口在 ConnectManagerV2 里：

这个错误在纯静态阶段完全发现不了，因为代码里两处都”讲得通”。最后是靠远程上真机全端口扫描、再回源码比对才定位的。

5.4 帧格式：收发魔数不对称

协议本身很简单：

但最初写的发送魔数是 FF FF E0 4A，抓到的实际是：发送用 00 00 E0 4A，投影仪回包用 FF FF E0 4A。解析时只认低 16 位 E04A 就行了。

5.5 按键码：常量名会骗人

按键命令是 {"action":50036,"commonCmd":{"type":"inst","action":"1/2","code":"N"}}，1 按下、2 抬起。第一版真机测试时用户反馈：

  • 点「电源」弹出的是快捷菜单；
  • 点「静音」弹出的是关机菜单；
  • 点「菜单」弹出的是导航栏编辑菜单。

原因是部分按键码在 smali 里是通过寄存器传进来的，静态抽取时对错了号。重新从 GMKeyTcpCommandFactory 逐个核对后：11 是关机菜单，12 是全部设置（快捷菜单），13 是立即关机，极米根本没有独立的静音键。

5.6 定时关机：传的是档位，不是时长

定时关机命令里有个 time 字段，第一反应传分钟数（15、30……），结果不管选多久，投影仪都提示”成功取消定时关机”。改成秒数还是一样。

最后在 UI 层的 PowerMenuDialog 里找到一句：

time 传的是档位编号：0 取消、1 = 15 分钟、2 = 30 分钟、3 = 1 小时、4 = 2 小时。只看协议层的方法签名 sendPowerOffDelay(int)，永远猜不到这一点，必须追到调用它的界面代码。

5.7 画面校正：找对入口

源码里叫”梯形校正”的方法不止一个。一开始用的是 openTrapezoidalCorrectionUi（action 45000），投影仪回 state:1 表示成功，但画面上什么都没发生。

后来顺着原版”工具”页面的点击逻辑往下追，发现画面校正走的是 ToolManager.sendAutoKstSystemDevice → sendCommonCmd(50028)，命令是一个几乎空的 JSON：

发出去之后，投影仪先打一片白光，然后画面从梯形调整回矩形——和原版一模一样。教训：协议层有很多”能用”的方法，要以 UI 实际调用的那条为准。

5.8 自动对焦：还原到字节级，依然失败

这是唯一没解决的功能，也最能说明静态分析的天花板。

原版点「自动对焦」，代码路径很清楚：ToolsManager.open("auto_focus") → ToolManager.autoFocus() → DeviceProxy.openAutoFocus() → 发 {"action":45984, "controlCmd":{"mode":32,...}, "msgid":"2"}。主页快捷工具和遥控器「更多」里的入口最终都汇到这一条。

依次排除的可能：

假设 验证方法 结果
握手不完整，投影仪不认这个控制端 按原版补全 authCode 的全部字段（authState/ip/phoneName/phoneUid/timeOut） 仍然失败
JSON 字段不一致 发现原版的 GsonUtils 开了 serializeNulls()，按字段声明顺序把所有 null 字段都补上，逐字节还原 仍然失败

走了别的通道 查蓝牙（只用于唤醒和配网）、查 Pandora 容器、查 F1 键 都不是

还有个意外发现：有一次测试脚本的引号被 PowerShell 吞掉，发出去的 JSON 格式根本不合法，投影仪回的也是同样的”未知错误”，说明它只是按 action 找到处理函数，然后在投影仪内部执行失败了。剩下的可能藏在投影仪端（比如对焦服务要求某种前置状态），或者原版在点击前后做了某件日志里看不到的事。要继续查，就得对原版做运行时插桩（Frida 之类），成本和收益已经不成比例，于是先隐藏了这个功能。

六、真机验证：真正起决定作用的环节

回头看，解决问题的从来不是”读得更仔细”，而是”在真机上发一条命令看看”。端口、魔数、按键码、定时关机、画面校正，全都是真机一测就露馅，改完再测就确认。

问题是投影仪不在我手边。这里用上了我自己写的 remote-assist-tool：家里电脑跑一下 share，把协助码发给 Claude Code，它就能在那台电脑上：

  • 扫描投影仪端口、用 PowerShell 写个小脚本直接发协议帧并打印回包；
  • 通过电脑上的 adb 给手机装包、截屏、抓 logcat；
  • 我在投影仪前面看效果，口头反馈”有了 / 没反应”。

中间还形成了一条很重要的工作约定，是我在过程中明确提出来的：先用脚本直接发命令，在真机上确认有效，再改 App、打包让我测。早期几轮是”改代码 → 打包 → 装手机 → 我测 → 不行再改”，一轮十几分钟，而且每次都是拿未验证的猜测让人测。改成先发命令之后，一条命令几秒钟就能知道对不对。

另一个经验是：测试脚本要保持连接。早期的脚本发完命令立刻断开，有些需要投影仪弹界面的命令就看不出效果；改成发完再等几秒、把这段时间的回包都收下来，判断准确了很多。

七、构建和打包的小坑

  • 公司网络拦截 Google Maven：Gradle 解析 Android Gradle Plugin 失败。把 Flutter 的 Gradle 设置和项目仓库统一指到阿里云镜像后解决。中间尝试过改成 buildscript classpath 的老式写法，结果 Kotlin 插件出现类加载器分裂的报错，又改了回来。
  • 包体积：debug 包 181MB，第一版 release 包 15.2MB。用 unzip -lv 一看，libflutter.so 和 libapp.so 是以 Stored（不压缩）方式放进 APK 的，两个加起来 15.4MB。加上 packaging.jniLibs.useLegacyPackaging = true 让原生库压缩存储，再开 R8 和资源压缩、去掉没用到的 cupertino_icons，最后 7.0MB。代价是安装后原生库要解压，占用的存储空间会多一些。
  • 小米手机 USB 安装：会被系统拦截（INSTALL_FAILED_USER_RESTRICTED），需要在手机上手动确认；网络 adb 偶尔 device offline，断开重连即可。

八、REA 的评价与局限

在这次的体验基础上，说说我对 REA 的看法。需要先声明：它的核心能力我基本没用上，所以下面更多是”上手门槛”层面的感受，而不是对它分析能力的评测。

做得好的

  • 诊断很准：doctor 准确区分了”注册正常”和”当前会话已连接”，报错也直接给出缺什么、怎么补，没有含糊；
  • skill 写得很有章法：先按目标类型选工具、先摘要再深入、区分观察与推断、把目标内容当不可信数据——即使最后没用 REA，这套方法论对 AI 做逆向也有指导意义；
  • 不擅自装东西：所有分析引擎都由用户自备，版本可控。在企业环境里这其实是优点。

局限

  • “自备引擎”的门槛：Android 要 JADX MCP JAR，原生二进制要 Ghidra/IDA/Hopper，固件要 Binwalk/Unblob。工具清单里能看到 207 个能力，但开箱即用的只是一小部分；
  • 受限网络下成本更高：本来下载一个 JAR 的事，在公司网络里就要绕路；
  • 工具数量带来的上下文开销：207 个工具的定义本身就很长，每次对话都要带上，会占用相当一部分上下文；
  • 静态分析解决不了运行时问题：这次真正卡住的地方（端口、档位、自动对焦）都需要真机验证。REA 也有 adb、Frida 等运行时能力，但前提是 agent 能直接接触到设备——而我的设备不在手边，最后靠的是另一个工具；
  • 对”简单目标”有点重：对一个没加固、没混淆的 APK，apktool + grep 足够了。REA 的价值大概在更复杂的场景：加固、混淆、原生代码、需要证据链和多次分析结果对比的时候。

也说说 AI 本身的局限

  • 静态分析时很自信，但错了好几次：端口、魔数、按键码、定时关机参数，静态结论都”讲得通”，但都错了。AI 读代码的速度很快，但”读对”仍然要靠真机验证兜底；
  • 会话中断：安全分类器拦截了两次回复（第一次就发生在刚提出”去掉登录”这个需求的时候，之后 AI 把方向调整为分析鉴权架构、做局域网互操作，才继续下去），还有上下文压缩、输出长度超限。长任务里这些中断会打断节奏，需要靠阶段性总结和笔记文件来接续；
  • 需要人类做眼睛：投影仪上有没有出现白光、对焦动画，只有人在现场才看得到。

九、结语

这次实验的标题本来应该是”用 REA 逆向极米助手”，最后变成了”在 REA 的指导思想下，用 apktool、grep、PowerShell 和一个远程协助工具，把协议一点点试出来”。

REA 的理念是对的：逆向要讲证据，要区分观察和推断，要对目标内容保持警惕。但它现阶段更像一个需要用户自己配齐引擎的”框架”，而不是开箱即用的”工具”。下次遇到加固或原生代码的目标，我会提前把 JADX 和 Ghidra 配好，再给它一次机会。

至于这个遥控器——除了自动对焦，日常用已经够了。不用登录，不用等 208MB 的 App 启动，打开就是遥控器，这就是我想要的。
