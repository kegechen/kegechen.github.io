> 远端是一台 Windows（或 Linux），藏在 NAT 后面，没开 SSH，也不想为它开 SSH。我想要的是：对方跑一条命令，把屏幕上那段话复制给我本地的 AI 助手——Claude Code、Codex、豆包都行，只要支持 MCP——它就能在那台机器上执行命令、读写文件、翻日志、传安装包。
>
> 从 2026 年 3 月到 10 月，这个想法长成了 [remote-assist-tool](https://github.com/kegechen/remote-assist-tool)：177 个提交、约 5.4 万行 Go（其中测试 1.7 万行）。本文按时间线讲它想解决什么、中间踩过哪些坑、为什么改成现在这样，以及它能做什么、做不到什么。

## 一、要解决的问题

### 1.1 场景

我日常要协助排查的机器大致有三类：

- 同事或现场的 Windows 电脑：装了一堆业务软件，出问题时要看日志、查进程、替换个 DLL；
- 局域网里的 Linux / ARM64 小机器：开发板、测试机；
- 跨网络的机器：在别人的 NAT 后面，没有公网 IP。

传统做法是远程桌面（向日葵、TeamViewer、RDP）加人肉操作。2026 年我的工作方式已经变成"大部分排查让 AI agent 动手"（我自己主要用 Claude Code），远程桌面对 AI 并不友好：它要的是结构化的命令执行和文件读写，而不是一个视频流。

### 1.2 为什么不直接用 SSH

SSH 是这类需求的标准答案，AI agent 也能直接通过 `ssh host cmd` 干活。问题出在远端是 Windows 的时候：

| 环节 | 在 Windows 上的实际体验 |
|---|---|
| 安装 sshd | OpenSSH Server 是"可选功能"，要管理员权限；内网机器常常装不上（Windows Update / FoD 源不可达） |
| 启动与防火墙 | 要手动把服务设成自启、放行 22 端口，有的机器还有组策略或安全软件拦着 |
| 密钥登录 | 管理员账号的公钥要放 `administrators_authorized_keys`，ACL 权限不对就静默失败 |
| 默认 shell | 进去是 `cmd.exe`，中文输出是 GBK，引号转义规则和 POSIX 完全不同 |
| 网络可达 | 机器在 NAT 后面，还得再配端口映射、frp 或者 VPN |
| 对方的心理负担 | "帮我开一下 SSH 服务、开一下防火墙"，对非开发同事来说这句话很难执行 |

这里面每一项单独看都能解决，但叠在一起，每次协助前都要先花半小时"让对方配环境"，而且装上的 sshd 是常驻服务，协助完还得记得关。

所以目标很明确：**被协助端零配置、免安装、不需要管理员权限、不开监听端口、能穿 NAT；协助端能让 AI 直接用。**

## 二、现在长什么样

一共三个角色：

![remote-assist-tool 架构](/img/remote-assist-tool/architecture.svg)

- **share**：被协助端跑 `remote share`（Windows 下双击 exe 也行），向 relay 注册，拿到协助码，然后把一整段"可以直接贴给 AI"的协助文案复制到剪贴板；
- **help**：协助端把 `remote help --mcp-stdio` 配成 AI agent 的 MCP server，agent 调 `connect(code, server)` 就配对成功。它是标准的 stdio MCP server，不绑定任何一家：Claude Code、Codex、豆包等支持 MCP 的 agent 都能接；
- **relay**：中转服务器，负责发协助码、转发消息，并辅助 P2P 打洞。

关于 relay 怎么选，有三种用法：

| 用法 | 什么时候用 | 怎么做 |
|---|---|---|
| 默认公共 relay | 开箱即用，大多数情况 | 什么都不用配。客户端内置了一台部署在**海外**的公共 relay |
| 自建 relay | 默认 relay 连不上或太慢；或者不想把信任交给别人的服务器 | 从 [GitHub Release](https://github.com/kegechen/remote-assist-tool/releases/latest) 下载 `remote-assist-relay-<os>-<arch>`，在两端都能访问的机器上运行并放行 TCP 8443，两端用 `--server` 或环境变量 `REMOTE_RELAY_SERVER` 指向它 |
| `--standalone` | 两端在同一个局域网 | `remote share --standalone`，relay 直接内嵌在 share 进程里，不依赖任何外部服务 |

Release 里 Windows / Linux / macOS 的 amd64、arm64 都有现成的 cli、relay 和 webui，另外还有一键安装脚本，下载后会用 `SHA256SUMS` 校验。

配对之后，agent 能用到 12 个工具：`connect`、`exec`、`read_file`、`write_file`、`list_dir`、`stat`、`glob`、`grep`、`process_list`、`tail_log`、`upload_file`、`download_file`。其中 `connect` 和上传下载在 help 端实现，其余在 share 端的工具 daemon 里执行（share 端另有一个内部用的 `file_md5`）。

另外还有一个浏览器控制台（`remote-assist-webui`），给人用：文件树、流式终端、搜索、进程、上传下载、图片预览，以及"通道内热升级远端 share"。它走的是和 AI agent 完全相同的 MCP 协议。

## 三、演进时间线

| 时间 | 阶段 | 关键词 |
|---|---|---|
| 2026-03 | SSH 隧道中转工具 | relay、协助码、TLS、STUN、P2P 打洞 |
| 2026-03 ~ 04 | 把 P2P 做可靠 | UDP 可靠传输、对称 NAT、UDP 中继回落、LAN 快速通道、代理旁路 |
| 2026-05 | 转向：给 AI agent 开 MCP 工具通道 | MCP、9 个工具、AEAD、bootstrap 模式 |
| 2026-06 ~ 08 | 能用 → 好用 | standalone、文件传输、续传、流式 exec、浏览器控制台、热升级、一键安装 |
| 2026-09 | 安全加固 | 静默失效、TOFU 证书钉扎、打洞包认证、工具协议 v2、抗重放 |
| 2026-09 ~ 10 | 兼容与体验 | `--min-proto` 向后兼容、代码页转码、传输进度条 |

最初的版本其实就是"SSH 隧道中转器"：help 端在本地监听一个端口，经 relay 转到 share 端的 22 端口。它解决了穿 NAT 的问题，但没解决"远端要有 sshd"的问题。5 月那次转向才是这个项目真正成型的地方：**不再转发 SSH，而是自己实现一套远程工具，直接暴露给 AI**。

## 四、踩过的坑

### 4.1 NAT 穿透：比想象中难得多

P2P 打洞的教科书流程是：两端各自向 STUN 问到自己的公网映射，交换地址，互相发 UDP 包。实际跑起来的问题一个接一个：

- **对称型 NAT**：每个目标地址映射一个新端口，STUN 问到的端口对对端没用。先加了 ±10 的端口预测，后来做了 NAT 类型检测（向两个不同 IP 的 STUN 查映射端口是否一致），对称 NAT 下扩大到 ±100，再加上"生日攻击"——本端开 64 个额外 socket 多轮发送，赌两边的端口撞上。
- **打不通的终究打不通**：加了 UDP 中继回落（经 STUN 服务器转发），auto 模式超时后先回落 relay，再在后台 30s/60s/120s 重试打洞，成功了再切过去。
- **同一个局域网绕了一大圈**：两端明明在同一个网段，却去公网绕。relay 侧检测双方是否同网（同公网 IP 或私网同 /16），给出 hint，客户端只以 50ms 间隔打私网地址，跳过 STUN 和公网打洞。
- **网卡选错了**：开着 Clash 之类 TUN 代理时，默认路由被劫持，打洞包从虚拟网卡出去；后来又遇到 VirtualBox Host-Only 网卡（192.168.56.x）——它不在黑名单里、有广播能力，被启发式选成"物理网卡"，可它根本没有外网路由。最后改成首选默认路由出口 IP，启发式只做兜底。

### 4.2 在 UDP 上自己造一个"TCP"

P2P 隧道是 UDP，上面跑的是需要可靠有序的数据。第一版加了序号、ACK、指数退避重传和按序交付，看起来能用了。直到开始传大文件：

- **没有流控**：发送端一口气把数据全怼出去，接收缓冲一满就丢，大文件在 offset 0 就 EOF；
- **重传 5 次就拆隧道**：网络稍微抖一下，单个包重传超限，整条隧道就被判死，大约每传几 MB 断一次。

修法是加发送窗口（`maxInflight` + 条件变量），重传退避封顶但**不再因为单包失败拆隧道**，隧道生死只看 peer 超时。这件事的教训是：在 UDP 上补可靠性，流控和"什么时候判死"跟重传一样重要。

### 4.3 "MCP 又挂了"：一条请求拖死整个会话

接入 agent 之后（最早是在 Claude Code 上跑），最常见的反馈是"MCP 断了 / No such tool available"。逐个查下来，是几种不同的"一处卡住、全局冻结"：

1. **空闲两分钟后必死**：help 端没开心跳，只靠 2 分钟读超时兜底。空闲期间读超时触发，读循环退出；下一次工具调用发出去后永远等不到响应，MCP server 被卡死，宿主判定它死亡并杀掉进程。修法：help 端 30 秒心跳，单次调用加硬超时。
2. **一条慢调用堵死所有调用**：MCP server 原本是串行读 stdin，`tools/call` 同步阻塞，期间连取消通知都读不到。改成工具调用并发分发，按 JSON-RPC id 登记可取消的 context，把 `notifications/cancelled` 真正接通。
3. **半死的隧道上写操作永久阻塞**：写阻塞时还占着连接锁，心跳、读超时设置、读循环跟着一起冻住。写操作加 30 秒超时；share 端每个工具请求都有按工具分档的兜底 deadline，Dispatch 放进 goroutine 和计时器赛跑——**任何请求都必须有返回**，哪怕是 `deadline_exceeded`。

### 4.4 P2P 和工具握手的死锁

工具通道需要先握手协商会话密钥。最初的流程是 help 在 relay 上等握手应答，而 share 一旦 P2P 建立，就转去 P2P 上等 help 的模式头——两边互相死等，connect 15 秒超时。P2P 越快建立越必现，同机、局域网场景百分之百触发。

先修成"先纯协商 P2P，结果决定在哪条通道握手"，后来又进一步改成**握手永远锚定在 relay 上，P2P 只在后台协商，双向探活通过后热切换，隧道中断就回落 relay 并重新握手**。控制面固定、数据面可切换，时序问题就少了一大类。

### 4.5 文件传输：比"循环调 write_file"复杂

`upload_file` / `download_file` 是在 help 端拼出来的复合工具，循环调用远端的 `write_file` / `read_file`，所以远端 share 不需要升级就能用。分块大小选 512 KiB：base64 之后约 683 KB，给 MCP 的 1 MB 帧留出余量。

后面的演进几乎全是在处理"网络会断"：

- **续传不能信调用方**：写成功了但响应丢了，help 以为失败再追加一次，文件就膨胀出整数个 chunk。改成续传点以**远端 stat 到的实际大小**为准。
- **并发写会留洞**：为了提速做过 8 路并发上传（`write_file` 带绝对偏移，pwrite 幂等可乱序），但并发写失败会在远端留空洞，"按 stat 大小续传"就不安全了——会跳过空洞，文件损坏。最后退回顺序上传：吞吐在高 RTT 下下降，但换来续传正确。**正确性优先于速度**。
- **断线自动重连续传**：隧道断开时用缓存的协助码自动重连，从断点继续，不需要人工介入。
- **进度显示**（2026-10 最新的一次改动）：share 端原来每个分块打一行日志，300 MB 就是 600 行刷屏。现在聚合成一行原地刷新：

```
上传 xgimi_remote.apk [==========>         ]  50.0%  150.0 MB/300.0 MB  8.1 MB/s  剩余 00:18
```

这个功能写起来比看上去难。help 端要在分块里额外带上文件总大小（`total`，旧版 share 会忽略这个字段）；慢链路上块与块之间隔几秒很正常，不能拿"空闲 3 秒"判结束；重试的分块要按偏移去重；收尾后迟到的重试要吞掉，但得写审计日志；中文要按 2 列计算终端宽度；进度行还不能和其他日志粘在一起。最后是在真实控制台里，用 `ReadConsoleOutputCharacter` 把屏幕读出来截帧验证的。

### 4.6 输出是给 AI 看的

工具的输出要被大模型读，这带来几个和"给人看"不同的要求：

- **别给 base64**：`[]byte` 默认被 JSON 编码成 base64，模型读不懂还费 token。改成合法 UTF-8 直接给文本，二进制只标注大小。
- **截断要保留尾部**：编译错误、panic 堆栈、测试失败摘要几乎总在输出末尾，从头截断恰好丢掉唯一有用的部分。统一改成保留首尾、省略中间，显式标记截断，并给出调大上限的参数。
- **中文 Windows 的代码页**：`ping`、`systeminfo`、cmd 内置命令输出的是 CP936（GBK），被当成二进制整段丢弃，agent 只能换种方式重跑。现在 share 端按活动代码页用 `MultiByteToWideChar` 转成 UTF-8 再上行，转不动的才原样透传。

### 4.7 安全：从"看起来安全"到"真的安全"

这是花时间最多的部分，也是最有收获的部分。

**第一课：别搞安全剧场。** 最初有个 `--root` 参数，把文件工具限制在某个目录里。后来意识到它挡不住 exec——一行 `sh -c 'cp x <root>/'` 就绕过去了。把它当安全边界，就是安全剧场。于是把它重新定位成可选的"防手滑护栏"，在文档里写明：真正的信任边界是"协助码交给了谁"，要隔离就上容器或低权限账号。

**第二课：最危险的是静默失效。** 一次集中排查，找出三处"出错了但没有任何信号"的问题：

1. Windows `--elevate` 提权重启时，参数被朴素地用空格拼接，`--root "C:\Work Dir" --allow-exec git,go` 在空格处被撕开，Go 的 flag 解析在第一个位置参数处停止，**`--allow-exec` 白名单被整个吞掉**——用户以为拿到的是"管理员 + 收紧的白名单"，实际是"管理员 + 放行一切"。
2. relay 对工具消息按"条数"限流，流式 exec 输出一个大日志就超限，超限的帧被**直接丢弃**；而每帧有独立的 AEAD nonce，丢一帧不影响后续解密，两端谁都察觉不到，输出中间少了几 KB。
3. 流帧的序号 share 端写了、help 端从来不看。

修法分别是：按 `CommandLineToArgvW` 规则转义参数，并拒绝任何残留的位置参数；限流改成按字节计费，超限时用 TCP 背压而不是丢帧；校验序号连续，有空洞就把整次调用判为失败。原则只有一条：**护栏失效时，宁可失败得刺眼。**

**第三课：加密不等于认证。** 工具通道用协助码经 HKDF 派生会话密钥，载荷用 XChaCha20-Poly1305 加密。但请求里只有参数是密文，工具名、调用 id 都是明文——截获一条 `read_file{path: X}` 的密文，把工具名改成 `write_file` 重发，远端解出来是 `Content=nil`，按截断模式打开文件，X 就被清成 0 字节。工具协议 v2 因此做了三件事：

- **AAD 绑定**：明文字段（工具名、id、deadline、流帧的 seq）都进 AAD，带长度前缀防止拼接歧义，三个方向各用不同标签；
- **强制密文**：握手后不带合法密文的请求一律拒绝（原来"没有 args 就跳过解密"等于留了个后门）；
- **抗重放**：按调用 id 做 1024 位滑动窗口，语义和 IPsec 一样。

v2 写完后又复审了两轮，每轮都找出真问题：响应方向的 `ok` / `error_code` 也是明文，把 `result` 删掉就能把一次成功的 `read_file` 伪造成"成功 + 空文件"——AI 会据此断定文件是空的；一条本地合成的 `server_busy` 绕过了加封路径；先记录序号再解密，让伪造的空帧可以"填平"丢帧检测。

**第四课：信任要有锚点。** relay 默认用自签证书，客户端默认跳过校验——这意味着中间人永远可行，而且不留痕迹。现在用 TOFU（首次信任）：第一次连接时记下证书指纹，之后指纹变了就拒连，攻击窗口从"永远"缩小到"仅首次"。P2P 打洞包原来只靠 session ID 识别对端，而 session ID 在打洞时会被喷到一大片端口上，根本不是秘密；现在打洞包带上用协助码派生的 HMAC，并做域分离。

**第五课：兼容是新版本的责任。** v2 和旧版 0.0.x 在会话层完全不通。最终方案是默认拒绝 v1，新版可以用 `--min-proto=1` 显式降级与旧版互通，并检测降级篡改。旧版没有这个参数，所以兼容的责任只能落在新的那一端。

## 五、能做到什么

- 被协助端一条命令（或双击），**不需要管理员权限、不需要安装**，默认模式下也不开监听端口（只主动连出去）；Windows、Linux、macOS 的 amd64 / arm64 都支持，提供一键安装脚本；
- 穿 NAT：P2P 直连优先，打不通自动回落中转；默认用内置的海外公共 relay，连不上就从 Release 下载 relay 自建，局域网内可以用 `--standalone` 完全不依赖外部服务；
- Claude Code、Codex、豆包等任何支持 MCP 的 agent 直接执行命令、读写文件、grep、看进程、跟踪日志、传大文件（断线自动续传，有进度显示）；
- 被协助端的屏幕上实时显示 AI 在做什么，每条操作都有审计日志；
- 人也能用：浏览器控制台有文件树、流式终端、上传下载，还能在不断开连接的情况下热升级远端的 share；
- relay 可以部署成 Linux 服务或 Windows 原生服务，带分层限流、资源上限和 slowloris 防护。

## 六、优势与不足

### 优势

- **对被协助方极其友好**：从"请开一下 SSH、开一下防火墙"变成"跑一下这个、把这段话发给我"；
- **为 AI 设计**：工具的 schema、输出格式、截断策略、错误信息都是按"给 LLM 读"来调的；
- **网络适应性强**：P2P、中转、局域网直连自动选择，断线自动重连；
- **透明**：被协助端能看到每一条操作，协助结束关掉进程就什么都不留。

### 不足与做不到的事

- **不是远程桌面**：没有 GUI 画面，点不了按钮。需要看界面的场景还得配合远程桌面工具；
- **没有交互式终端**：exec 是"一条命令一次返回"（支持流式输出），跑不了需要交互输入的程序，`vim`、`top` 这类 TUI 也不行；
- **不做通用端口转发**：老的 `--legacy-ssh` 隧道模式还在，但只能转发到 share 端 `--ssh` 指定的那一个地址；
- **relay 是可信边界**：协助码由 relay 生成，密钥派生的输入在 relay 侧全部可见。也就是说，relay 失陷就能解密、伪造活动会话的工具数据。默认的公共 relay 方便试用，敏感环境请**自己部署 relay**，不要用来路不明的中转。写这篇文章时回头核对，发现 README 里一直写着"即使 relay 被攻破，也看不见、无法伪造工具内容"，跟实现不符，已经更正（[4340cd1](https://github.com/kegechen/remote-assist-tool/commit/4340cd1)）；同时补上了默认 relay 在海外、如何自建的说明（[514117f](https://github.com/kegechen/remote-assist-tool/commit/514117f)）；顺手把文档和命令行提示里写死的"给 Claude 用"统一改成了"任何支持 MCP 的 AI agent"，README 也换上了文中这张架构图（[05ed347](https://github.com/kegechen/remote-assist-tool/commit/05ed347)）；
- **协助码就是全部权限**：拿到协助码等于能在那台机器上以当前用户执行任意命令。`--root` 和 exec 黑白名单只防手滑，不是安全边界；
- **文件上传是顺序的**：为了续传正确牺牲了高延迟链路下的吞吐，回环上大约 8～10 MB/s；
- **自签证书 + TOFU** 只能防"首次之后"的中间人，首次连接仍需在可信网络下完成；
- **没有发布签名**：一键安装校验 SHA256，但校验文件和二进制来自同一个 Release，防不了 Release 本身被替换。

## 七、怎么开发的：和 Claude Code 结对

这个项目的大部分代码是我和 Claude Code 结对写出来的——177 个提交里，绝大多数带着 `Co-Authored-By: Claude`，跨越了 Opus 4.6 到 Opus 5.5 好几代模型。顺带一提，这个工具本身就是给 AI agent 用的，所以后期很多调试也是让 Claude Code 通过它去调试远端机器完成的。

半年下来，最有价值的不是"AI 写得快"，而是几条逐渐固定下来的工作约定：

- **动手前先查 git 历史**。很多"看起来不对"的代码，其实是当初为了解决某个问题刻意写成那样的；"修"掉它，原来的问题就回来了。比如顺序上传，就是从 8 路并发退回来的。
- **没跑红的测试不算数**。每个新测试都要先把被测逻辑中性化（把判断改成 `if false`、让函数直接返回），确认测试会失败，再恢复确认通过。传输进度那个功能前后做了三十多处这种 RED 证明，其中有几处变异后测试依然是绿的——有的暴露出测试写得太弱，有一处则说明那段判断根本是死代码，于是删掉了。
- **复审循环直到挑不出问题**。每轮修复本身也是新代码，也要被审。协议 v2 复审了两轮才收敛，进度条功能审了三轮，每轮都能在上一轮的加固代码里找出真问题。
- **最后在真实环境跑一遍**。单元测试全绿的进度条，在真实控制台里一跑，发现每次传输都多出两行和屏幕汇总重复的审计日志，小文件还显示了没有意义的"平均 236 KB/s"。

## 八、结语

回头看，这个项目最初只想解决"Windows 上开 SSH 太麻烦"，后来变成了一个更有意思的问题：**怎么给 AI 一双安全、可靠、能穿越网络的手**。网络层的坑靠耐心一个个填，"为 AI 设计输出"是个新问题，而安全这块最大的收获是心态上的：别满足于"加了密"，要去问"失效时有没有信号"、"信任的锚点在哪里"。
